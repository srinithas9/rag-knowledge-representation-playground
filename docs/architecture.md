# Architecture — RAG Knowledge Representation & Retrieval Playground

## 1. Purpose

The **RAG Knowledge Representation & Retrieval Playground** is a comparative RAG system designed to study how different ways of representing knowledge and different retrieval strategies affect:

1. the evidence retrieved,
2. the quality and relevance of that evidence, and
3. the final answer generated by an LLM.

The project uses one common knowledge source — the **NovaMart Customer & Operations Policy Handbook — 2026** — and represents the same underlying knowledge in multiple ways.

The project compares four primary knowledge representations:

* Text / Chunked Text
* Text + Metadata
* Structured Data
* Knowledge Graph

These representations are then tested with retrieval strategies that are appropriate to each representation.

The central research question is:

> **How does the combination of knowledge representation and retrieval strategy affect the evidence retrieved for the same question, and how does that evidence affect the final RAG answer?**

# 3. Core RAG Pipeline

The project separates knowledge representation, storage/indexing, retrieval, evidence, and answer generation.

```text
Source
   ↓
Parse / Normalize
   ↓
Knowledge Representation
   ↓
Storage / Index
   ↓
User Query
   ↓
Retrieval Strategy
   ↓
Evidence[]
   ├──────────────→ Retrieval / Evidence Evaluation
   │
   ↓
LLM
   ↓
Answer
   ↓
Answer Evaluation
```

This separation is important because an incorrect final answer can originate from different stages of the pipeline.

For example:

```text
Representation problem
        ↓
Poor retrieval
        ↓
Poor evidence
        ↓
Wrong answer
```

or:

```text
Good representation
        ↓
Good retrieval
        ↓
Correct evidence
        ↓
LLM fails to use evidence correctly
        ↓
Wrong answer
```

The architecture therefore evaluates retrieval/evidence **before relying on the final LLM answer**.

# 4. Knowledge Representation Layer

The representation layer determines **how the NovaMart knowledge is organized**.

The four representations are independent.

---

## 4.1 Text / Chunked Text

Folder:

```text
representations/text/
```

The source knowledge is converted into searchable text units/chunks.

Each chunk should preserve source traceability.

Example:

```text
chunk_id
source_id
content
metadata
```

The pair is responsible for:

* extracting source content,
* cleaning the text,
* designing chunk boundaries,
* creating chunks,
* preserving source IDs,
* storing/indexing the chunks,
* implementing a basic/native retrieval path,
* returning results using the common `Evidence` contract.

The representation should make it possible to study how chunking affects retrieval.

---

## 4.2 Text + Metadata

Folder:

```text
representations/text_metadata/
```

This representation combines searchable text with structured metadata.

Possible source-supported metadata includes:

```text
policy_area
customer_tier
region
product_category
effective_from
effective_to
promotion_id
seller_type
```

Metadata must come from the source data or normalized dataset.

The pair is responsible for:

* creating text units,
* attaching relevant metadata,
* preserving source IDs,
* choosing appropriate storage/indexing,
* implementing basic/native retrieval with metadata constraints,
* returning `Evidence[]`.

This representation allows the project to study whether explicit metadata helps retrieval preserve important constraints such as region, customer tier, or policy validity.

---

## 4.3 Structured Data

Folder:

```text
representations/structured_table/
```

Structured representation models knowledge using entities, attributes, and relationships.

Natural entities may include:

```text
Customer
Product
Manufacturer
Seller
Policy
Promotion
Region
Support Case
Order
```

PostgreSQL is the preferred storage technology unless there is a justified technical reason to use another relational database.

The pair is responsible for:

* identifying natural entities,
* designing the relational schema,
* defining relationships,
* creating the database schema,
* loading source data,
* implementing representative SQL retrieval,
* converting retrieved records into `Evidence[]`.

The goal is not to convert every sentence into a database row.

The focus is on knowledge that is naturally represented through structured entities and relationships.

---

## 4.4 Knowledge Graph

Folder:

```text
representations/knowledge_graph/
```

The knowledge graph represents entities as nodes and relationships as edges.

Example entities:

```text
Customer
Tier
Product
Category
Manufacturer
Seller
Policy
Promotion
Region
Order
Support Case
Escalation Level
```

Example relationships:

```text
Customer ──HAS_TIER──────> Tier
Customer ──PLACED────────> Order
Order ──CONTAINS─────────> Product
Product ──MANUFACTURED_BY> Manufacturer
Product ──PART_OF────────> Category
Product ──QUALIFIES_FOR──> Promotion
Promotion ──USES─────────> Policy
Policy ──APPLIES_TO──────> Region
```

The pair is responsible for:

* identifying entities,
* identifying relationships,
* creating the graph,
* populating the graph,
* preserving source traceability,
* implementing basic/native graph traversal,
* returning graph-derived evidence as `Evidence[]`.

The representation should be particularly useful for relationship-heavy and multi-hop questions.

# 5. Representation vs Storage vs Retrieval

These are separate concepts.

### Representation

How the knowledge is organized.

Examples:

```text
Text
Text + Metadata
Tables
Graph
```

### Storage / Index

Where or how the representation is persisted and made searchable.

Examples:

```text
Text index
Vector store
PostgreSQL
Graph database
```

### Retrieval

How relevant knowledge is found.

Examples:

```text
Keyword search
Semantic/vector search
Hybrid search
Metadata filtering
SQL queries
Graph traversal
Reranking
```

Therefore:

> A vector database is not itself a knowledge representation.

For example:

```text
Text representation
        ↓
Vector storage/index
        ↓
Semantic retrieval
```

Similarly:

```text
Structured representation
        ↓
PostgreSQL
        ↓
SQL retrieval
```

And:

```text
Graph representation
        ↓
Graph store
        ↓
Graph traversal
```

Keeping these concepts separate is essential to the project's comparison.

# 6. Phase 1 — Representation Readiness

In Phase 1, each pair owns its representation **end-to-end enough to prove that it works**.

The Phase 1 flow is:

```text
SOURCE
   ↓
REPRESENT
   ↓
STORE
   ↓
BASIC / NATIVE RETRIEVAL
   ↓
Evidence[]
```

Each pair therefore needs to answer:

> Can our representation correctly preserve the relevant knowledge, store it, retrieve it, and return traceable evidence?

### Phase 1 responsibilities

Each pair should:

1. Understand the common source.
2. Design the representation.
3. Transform the source into that representation.
4. Store/index the representation.
5. Implement a basic/native retrieval path.
6. Test representative questions.
7. Inspect the retrieved evidence.
8. Return results through the common `Evidence[]` contract.
9. Document limitations and failure cases.

---

# 7. Phase 1 Testing

Phase 1 does **not** require an LLM to prove that retrieval works.

The primary output is retrieved evidence.

The test flow is:

```text
Source
   ↓
Representation
   ↓
Storage
   ↓
Question
   ↓
Basic Retrieval
   ↓
Top-K Evidence
   ↓
Compare with Ground Truth
```

For example:

```text
Question:
"What is the refund period for a Premium customer in India?"

        ↓

Basic Retriever

        ↓

Top-K Evidence

        ↓

Inspect:
- Was the correct policy retrieved?
- Was it ranked highly?
- Is the evidence complete?
- Is the source traceable?
- Was an outdated policy retrieved?
- Was an exception missed?
```

This allows the team to identify retrieval failures before an LLM potentially hides them with a plausible answer.

# 8. Common Evidence Contract

All representation-specific retrieval implementations must return evidence using the same structure.

```python
from dataclasses import dataclass, field
from typing import Any

@dataclass
class Evidence:
    content: str
    source_id: str
    score: float
    metadata: dict[str, Any] = field(default_factory=dict)
```

The exact implementation may evolve, but the shared contract should remain stable unless the architecture is intentionally changed.

The common evidence object allows the evaluation layer to compare results from different representations.

# 9. Common Interfaces

## Knowledge Representation

```python
from abc import ABC, abstractmethod

class KnowledgeRepresentation(ABC):

    @abstractmethod
    def build(self, documents):
        pass
```

## Retriever

```python
from abc import ABC, abstractmethod

class Retriever(ABC):

    @abstractmethod
    def retrieve(
        self,
        query: str,
        top_k: int = 5,
        filters: dict | None = None,
    ) -> list[Evidence]:
        pass
```

The purpose of these interfaces is to provide a common integration contract without forcing every representation to use the same underlying technology.

# 11. Phase 2 — Retrieval Experiments

Phase 2 builds on the working representations from Phase 1.

The Phase 2 experiment flow is:

```text
SAME QUERY
     ↓
MULTIPLE REPRESENTATIONS
     +
MULTIPLE APPLICABLE RETRIEVAL STRATEGIES
     ↓
Evidence[]
     ↓
COMMON EVALUATION
     ↓
COMPARISON
     ↓
LLM
     ↓
FINAL ANSWER
```

Phase 2 focuses on questions such as:

* Which representation retrieves the required evidence?
* Which retrieval strategy retrieves it?
* How does ranking change?
* Does metadata improve retrieval for constrained questions?
* Do structured queries outperform unstructured retrieval for certain questions?
* Does graph traversal help with multi-hop relationships?
* Does reranking improve evidence quality?
* Where does each approach fail?

Advanced retrieval strategies belong primarily to the shared retrieval/experiment layer rather than being duplicated independently by all four pairs.

# 13. Evidence-First Evaluation

The project intentionally evaluates retrieved evidence separately from the final answer.

The main reasoning is:

> A good final answer does not automatically prove that retrieval was good.

An LLM may sometimes produce a plausible answer even when:

* the wrong policy was retrieved,
* the evidence is incomplete,
* an outdated policy was retrieved,
* an exception was missed,
* the relevant source was ranked too low.

Therefore, retrieval should first be evaluated directly.

---

# 14. Retrieval Metrics

Potential retrieval metrics include:

### Precision@K

Measures how much of the retrieved top-K evidence is relevant.

### Recall@K

Measures whether the required evidence was successfully retrieved.

### MRR

Measures how highly the first relevant result appears.

### nDCG@K

Useful when evidence has graded relevance rather than simply relevant/not relevant.

### Latency

Measures retrieval response time.

Metrics should be applied where they are meaningful for the representation and retrieval strategy.

---

# 15. Evidence Quality

In addition to numerical metrics, the project should inspect:

* required source IDs retrieved,
* evidence completeness,
* source traceability,
* ranking quality,
* irrelevant evidence,
* temporal correctness,
* constraint preservation,
* multi-hop completeness.

The benchmark should help identify specific failure modes rather than only producing one overall score.

---

# 16. Answer Evaluation

After retrieval/evidence evaluation, the same evidence can be passed to an LLM.

```text
Question
   +
Evidence[]
   ↓
LLM
   ↓
Answer
```

Answer evaluation can examine:

* correctness,
* groundedness,
* faithfulness,
* whether the answer is supported by retrieved evidence.

This separates:

```text
Retrieval failure
```

from:

```text
Answer-generation failure
```

# 17. Benchmark

The project uses a common benchmark containing:

```text

```

The benchmark covers different reasoning and retrieval requirements, including areas such as:

* direct lookup,
* structured information,
* temporal policies,
* exceptions,
* precedence,
* metadata constraints,
* multi-hop relationships,
* graph-oriented questions.

All representation teams use the same source and benchmark.

This ensures that comparisons are based on the same questions rather than separate datasets.

# 18. Failure Analysis

The project should document not only successful retrievals but also failures.

Important failure categories include:

### Semantic Near-Match

The retriever finds text that is semantically similar but does not actually answer the question.

### Wrong Policy Version

A historical or outdated policy is retrieved instead of the applicable version.

### Wrong Customer Tier / Region

The evidence matches the topic but does not satisfy the required customer or geographic constraint.

### Exception Ignored

A general rule is retrieved while a more specific exception is missed.

### Incomplete Multi-Hop Path

The system retrieves only part of the relationship chain needed to answer the question.

### Irrelevant Evidence Overload

Too much unrelated evidence is retrieved, making answer generation harder.

### Correct Answer with Unsupported Evidence

The LLM produces the correct answer, but the retrieved evidence does not actually support it.

These failure cases are important because they reveal **why** a RAG system succeeds or fails.

# 22. Git Integration

The project uses a branch-based Git workflow.

The basic workflow is:

```text
Clone repository
      ↓
Create pair branch
      ↓
Work within assigned scope
      ↓
Test changes
      ↓
Commit changes
      ↓
Push branch
      ↓
Open Pull Request
      ↓
Review
      ↓

```

Team members should not directly develop on `main`.

Shared/core files should not be changed casually because they affect all pairs.

Each contribution should clearly communicate:

* what changed,
* why it changed,
* how it was tested,
* what evidence/results were obtained,
* known limitations.

# 23. Definition of Done

A representation is considered ready for integration when:

* the representation is documented,
* source data has been transformed correctly,
* storage/index has been created,
* the representation can be queried,
* basic/native retrieval works,
* results are returned as `Evidence[]`,
* source IDs are preserved,
* representative questions have been tested,
* failure cases have been documented,
* tests or validation checks are included,
* the implementation works from a clean repository setup.

Phase 1 does not require the pair to implement every advanced retrieval strategy.

# 25. Design Principle

The core principle of this project is:

> **Do not evaluate only the final answer. Evaluate the evidence that produced the answer.**

The project should make it possible to determine whether a failure came from:

```text
Knowledge Representation
        ↓
Storage / Index
        ↓
Retrieval
        ↓
Evidence
        ↓
LLM
        ↓
Answer
```

This makes the playground useful not only as a demonstration of RAG techniques, but also as a learning and experimentation framework for understanding **why different representations and retrieval strategies behave differently**.
