# Architecture — RAG Knowledge Representation & Retrieval Playground

## 1. Purpose

The **RAG Knowledge Representation & Retrieval Playground** is a comparative RAG system designed to study how different ways of representing knowledge and different retrieval strategies affect:

1. the evidence retrieved,
2. the quality and relevance of that evidence, and
3. the final answer generated by an LLM.

The project uses one common knowledge source — the **NovaMart Customer & Operations Policy Handbook — 2026** — and builds multiple end-to-end retrieval pipelines from the same underlying knowledge.

The four primary pipelines are:

* Text / Chunked Text
* Text + Metadata
* Structured Data
* Knowledge Graph

The central research question is:

> **How does the combination of knowledge representation and retrieval strategy affect the evidence retrieved for the same question, and how does that evidence affect the final RAG answer?**

The project is an experimentation and comparison platform. It is **not an LLM training project**.

---

# 2. Core Architecture Principle

The project follows:

> **SAME KNOWLEDGE + SAME QUESTIONS + DIFFERENT REPRESENTATION / RETRIEVAL**

All pipelines use the same NovaMart source knowledge and the same official benchmark.

Each pair owns an end-to-end pipeline:

```text
Source
   ↓
Representation
   ↓
Storage / Index
   ↓
Basic / Native Retrieval
   ↓
Evidence[]
```

The integration layer can later run multiple applicable retrieval strategies and compare their results.

The overall architecture is:

# 3. End-to-End RAG Flow

The complete system can be understood as:

```text
Source Knowledge
      ↓
Knowledge Representation
      ↓
Storage / Index
      ↓
User Query
      ↓
Retrieval Strategy
      ↓
Evidence[]
      ↓
Retrieval / Evidence Evaluation
      ↓
Common LLM
      ↓
Final Answer
      ↓
Answer Evaluation
```

A failure can occur at multiple stages.

For example:

```text
Representation problem
        ↓
Poor retrieval
        ↓
Poor evidence
        ↓
Wrong answer
```

Or:

```text
Good representation
        ↓
Good retrieval
        ↓
Correct evidence
        ↓
LLM fails to use evidence correctly
        ↓
Wrong answer
```

Therefore, the project evaluates **retrieval and evidence separately from answer generation**.

# 4. Pipeline Architecture

Each pipeline follows the same high-level contract while using technology appropriate to its representation.

```text
                  COMMON NOVAMART SOURCE
                           │
                           ▼

                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
        Text           Metadata         Structured
      Pipeline         Pipeline          Pipeline
          │                │                │
          │                │                │
          └────────────────┼────────────────┘

```

More precisely, each pipeline independently performs:

```text
Source
  ↓

  ↓
Storage / Index
  ↓
Retriever
  ↓

```

This gives each pair ownership of a complete experimental unit.

# 5. Why Pipelines Are End-to-End

Representation and retrieval cannot always be designed independently.

Different representations naturally support different retrieval methods.

For example:

```text
Text
  ↓
BM25 / Keyword
Dense Vector
Hybrid
Reranking
```

Whereas:

```text
Text + Metadata
  ↓
Dense Retrieval
  +
Metadata Filtering
```

And:

```text
Structured Data
  ↓
PostgreSQL
  ↓
SQL Retrieval
```

And:

```text
Knowledge Graph
  ↓
Graph Store
  ↓
Graph Traversal
```

Therefore, the project does **not** force every representation to implement every retrieval technique.

The comparison should use technically meaningful combinations.

# 10. Representation vs Storage vs Retrieval

These are three different concepts.

## Representation

How the knowledge is organized.

Examples:

```text
Text
Text + Metadata
Structured Tables
Knowledge Graph
```

## Storage / Index

Where or how the representation is persisted and made searchable.

Examples:

```text
Text Index
Vector Store
PostgreSQL
Graph Store
```

## Retrieval

How relevant knowledge is found.

Examples:

```text
Keyword Search
Semantic / Vector Search
Hybrid Search
Metadata Filtering
SQL Queries
Graph Traversal
Reranking
```

Therefore:

> **A vector database is not itself a knowledge representation.**

For example:

```text
Text Representation
       ↓
Vector Index
       ↓
Semantic Retrieval
```

Similarly:

```text
Structured Representation
       ↓
PostgreSQL
       ↓
SQL Retrieval
```

And:

```text
Graph Representation
       ↓
Graph Store
       ↓
Graph Traversal
```

This distinction is essential to the project's experiments.

# 11. Common Evidence Contract

All pipeline retrieval implementations must return evidence using the common structure.

```python
from dataclasses import dataclass, field
from typing import Any

@dataclass
class Evidence:
    content: str
    source_id: str
    score: float
    metadata: dict[str, Any] = field(default_factory=dict)
```

The exact implementation may evolve, but the common integration contract should remain stable unless intentionally changed.

The purpose is to allow the evaluation and integration layers to compare results from different pipelines.

---

# 12. Common Retriever Interface

Retrievers should expose a common external contract even when their internal implementation is completely different.

Conceptually:

```python
from abc import ABC, abstractmethod

class Retriever(ABC):

    @abstractmethod
    def retrieve(
        self,
        query: str,
        top_k: int = 5,
        filters: dict | None = None,
    ) -> list[Evidence]:
        pass
```

The interface does **not** mean every pipeline must use the same retrieval technology.

It only defines how retrieval results are communicated to the rest of the system.

For example:

```text
Text Retriever
      ↓
Evidence[]

SQL Retriever
      ↓
Evidence[]

Graph Retriever
      ↓
Evidence[]
```

All three can therefore participate in common evaluation.

# 13. Phase 1 — Pipeline Readiness

Phase 1 establishes that each pair's pipeline works independently.

The flow is:

```text
SOURCE
   ↓
REPRESENT
   ↓
STORE / INDEX
   ↓
BASIC / NATIVE RETRIEVAL
   ↓
Evidence[]
```

Each pair should answer:

> **Can our pipeline preserve the relevant knowledge, store it correctly, retrieve it, and return traceable evidence?**

### Phase 1 responsibilities

Each pair should:

1. Understand the common source.
2. Design the representation.
3. Transform the source into that representation.
4. Store or index the representation.
5. Implement basic/native retrieval.
6. Test representative questions.
7. Inspect retrieved evidence.
8. Return results using the common `Evidence[]` contract.
9. Measure or record useful retrieval behaviour.
10. Document limitations and failure cases.

Phase 1 does **not** require an LLM.

The primary output is:

```text
Question
   ↓
Retriever
   ↓
Evidence[]
```

# 20. Retrieval Metrics

Potential retrieval metrics include:

### Precision@K

Measures how much of the retrieved top-K evidence is relevant.

### Recall@K

Measures whether required evidence was retrieved.

### MRR

Measures how highly the first relevant result appears.

### nDCG@K

Useful when evidence has graded relevance.

### Retrieval Latency

Measures how long retrieval takes.

Not every metric must be used for every experiment.

Metrics should be selected based on what the retrieval experiment is trying to measure.

---

# 21. Evidence Quality

Numerical metrics are not sufficient by themselves.

The project should also inspect:

* required source IDs retrieved,
* evidence completeness,
* source traceability,
* ranking quality,
* irrelevant evidence,
* temporal correctness,
* constraint preservation,
* multi-hop completeness.

This helps explain **why** a retrieval system succeeded or failed.

# 22. Answer Evaluation

After retrieval evaluation, the retrieved evidence can be passed to the common LLM.

```text
Question
   +
Evidence[]
   ↓
Common LLM
   ↓
Answer
```

Answer evaluation can examine:

* correctness,
* groundedness,
* faithfulness,
* completeness,
* whether the answer is actually supported by retrieved evidence.

This allows the project to distinguish:

```text
Retrieval Failure
```

from:

```text
Generation / Reasoning Failure
```

---

# 23. Retrieval vs Answer Diagnostic

A useful diagnostic model is:

```text
Retrieval ❌ + Answer ❌
        ↓
Likely retrieval bottleneck
```

```text
Retrieval ❌ + Answer ✅
        ↓
LLM may have inferred or already known the answer,
but retrieval was still unsuccessful
```

```text
Retrieval ✅ + Answer ❌
        ↓
Possible generation / reasoning failure
```

```text
Retrieval ✅ + Answer ✅
        ↓
Desired outcome
```

This prevents the final answer from hiding retrieval problems.

# 25. Failure Analysis

The project should document failures, not only successful results.

Important failure categories include:

## Semantic Near-Match

The retriever finds evidence that is semantically similar but does not actually answer the question.

## Wrong Policy Version

A historical or outdated policy is retrieved instead of the applicable version.

## Wrong Customer Tier / Region

The evidence matches the topic but does not satisfy the required customer or geographic constraint.

## Exception Ignored

A general rule is retrieved while a more specific exception is missed.

## Incomplete Multi-Hop Path

The system retrieves only part of the relationship chain required to answer the question.

## Irrelevant Evidence Overload

Too much unrelated evidence is retrieved, making answer generation harder.

## Correct Answer with Unsupported Evidence

The LLM produces the correct answer even though the retrieved evidence does not actually support it.

These failures are valuable because they reveal **why** a system succeeds or fails.

# 27. Comparison Philosophy

The project should not assume that one representation is universally best.

Instead, the comparison should answer:

> **Which approach works best for this type of question, under these constraints, and why?**

For example:

```text
Simple factual lookup
        ↓
Structured retrieval may be strong
```

```text
Region + customer tier + policy version
        ↓
Metadata-aware retrieval may be strong
```

```text
Multi-hop relationship
        ↓
Graph retrieval may be strong
```

```text
Broad natural-language policy question
        ↓
Text / semantic retrieval may be strong
```

These are hypotheses to test, not predetermined conclusions.

# 34. Core Design Principle

The most important principle of the project is:

> **Do not evaluate only the final answer. Evaluate the evidence that produced the answer.**

The playground should make it possible to determine whether a failure originated from:

```text
Knowledge Representation
        ↓
Storage / Index
        ↓
Retrieval
        ↓
Evidence
        ↓
LLM
        ↓
Answer
```

This makes the project useful not only as a demonstration of RAG techniques, but as an experimentation framework for understanding **why different representations and retrieval strategies behave differently**.
